# Legacy and reference project audit

Audit date: 2026-09-21  
FIG repository: `/home/enzoreacher/Forge-Gym-Health`  
Read-only references: `/home/enzoreacher/Forge-Gym-V2`, `/home/enzoreacher/Repos/open-webui`

## Executive conclusion

FIG already contains a functioning nutrition/activity/food-analysis backend and Expo vertical slice. It is not an empty repository. Forge-Gym-V2 provides a strong workout reliability skeleton but not a complete beginner workout product. Open WebUI provides useful browser interaction patterns but is tightly coupled to its own stack, product, and licensing. FIG should preserve valid existing backend work, adapt selected V2 behavior, and independently implement its web UI.

Classifications:

- **KEEP:** preserve the behavior or invariant as a FIG requirement.
- **ADAPT:** preserve the idea but redesign it for FIG's architecture/product.
- **FREEZE:** retain as historical evidence or deferred input; do not evolve or present as current FIG behavior.
- **REMOVE:** exclude generated/local artifacts from any migration.
- **REJECT:** do not adopt the approach.

## Decisions required before M2 workout implementation

1. Can one user have multiple active sessions?
2. Can one user have multiple sessions on one local date?
3. What happens to unperformed sets when a workout is finished?
4. Are skipped, cancelled, and abandoned distinct states?
5. How are completed records corrected without silently rewriting history?
6. Which metrics are required beyond load and repetitions?
7. Which entered/display unit metadata is retained?
8. What retry/idempotency retention window is required?
9. Is online-first sufficient through M3? The current recommendation is yes.

## Audit acceptance

The audit is accepted when task packets use these classifications as input rather than copying code, every adopted item receives FIG tests, references remain unmodified, and `docs/CURRENT_STATE.md` states the actual implementation rather than the desired architecture.
